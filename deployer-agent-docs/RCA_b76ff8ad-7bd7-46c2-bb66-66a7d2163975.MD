# RCA — ledgerkit.in checkout failure & stale deployment

## Problem statement
Live site `ledgerkit.in` (Cloudflare custom domain), page `/medical-6-combo`, "Buy for ₹199" → toast "Couldn't start checkout — The origin web server returned an invalid or incomplete response to Cloudflare…" (this is `err.response.data.detail` of `POST /api/checkout/create-order`). Live page shows ₹199 but this job's workspace shows ₹297, suggesting `ledgerkit.in` serves an OLDER deployment. A prior debug for this job reportedly failed with "v3 deployment not found".

## Investigation & evidence

### 1. Does this job have a deployment? — YES
- `describe_deployment_state`: deployment `ledgerkit-live` (deployment_id `5df89de2-c386-4c85-bad2-25c1638ec506`), job_id `5cccc821-9f25-4b6f-874c-7c6c2c771219`, active_run `b76ff8ad-7bd7-46c2-bb66-66a7d2163975` = **success**, frontend_type cloudflare, tier_0, cluster-05.
- Live default URL `https://ledgerkit-live.emergent.host/` → **200 OK**, real LedgerKit app content.
- The earlier "v3 deployment not found" was almost certainly scoped to the OTHER (older) job that currently owns `ledgerkit.in` — not this one. This job's deployment exists and is healthy.

### 2. Which deployment serves ledgerkit.in? — NOT this one (yet)
- `list_domains`: both `ledgerkit.in` and `www.ledgerkit.in` are attached to THIS deployment but `verified:false`, `ssl_status:"initializing"`.
- `check_domain_status`: both `linked:true` (DNS A-record resolves to Cloudflare).
- Because the custom hostname SSL is still "initializing"/unverified on this deployment, `ledgerkit.in` has **not cut over** to this deployment's Cloudflare worker. It is still served by the older deployment's worker — which renders ₹199 and throws the Cloudflare 52x origin error on checkout.
- Price proof the live site is an OLDER build: this job's source seeds the medical-6 combo at **₹297** (`backend/seed_data.py` `sale_price: 297`, edition `digital.price: 297`), whereas live shows ₹199.

### 3. Backend pod health & /api/checkout/create-order on THIS deployment — HEALTHY
- `GET /api/checkout/create-order` on default URL → **405 Method Not Allowed** = route exists, POST-only; backend is up.
- `fetch_app_logs` (run b76ff8ad, 1440m, filtered for checkout/razorpay/traceback/500/502): only `GET /health → 404` probe noise. No 5xx, no crash, no `pkg_resources`/`setuptools` import error.
- Note: the app has no bare `/health` route (returns 404) but `/` returns 200, so health_check passed. Harmless.
- Therefore the Cloudflare "invalid/incomplete response" (a CF 520/52x origin error) is NOT produced by this deployment — it originates from the old deployment currently serving `ledgerkit.in`.

### 4. Razorpay secrets in production — MISSING on this deployment
- `list_secrets` (active run b76ff8ad) keys: CORS_ORIGINS, DB_NAME, EMAIL_FROM_NAME, ENABLE_HEALTH_CHECK, INTEGRATION_PROXY_URL, MONGO_URL, REACT_APP_BACKEND_URL, REACT_APP_META_PIXEL_ID, SITE_BASE, WDS_SOCKET_PORT.
- **No RAZORPAY_KEY_ID, RAZORPAY_KEY_SECRET, PAYMENT_LIVE_KEY_ID, or PAYMENT_LIVE_KEY_SECRET.**
- Source reality (eph pod, run b76ff8ad): `backend/server.py` reads ONLY `RAZORPAY_KEY_ID` / `RAZORPAY_KEY_SECRET` (lines 25–26). **There is NO `PAYMENT_LIVE_KEY_*` in this job's code** — that naming is from the old deployment / the reporter's assumption.
- `backend/.env` in the pulled source contains only MONGO_URL, DB_NAME, CORS_ORIGINS, SITE_BASE, EMAIL_FROM_NAME — **no Razorpay keys**. So first-deploy/redeploy had nothing to seed, hence prod has none.
- Behavior without keys: `razorpay_client is None` → `create-order` raises **HTTP 503** "Payments are temporarily unavailable" (server.py line 256; confirmed by `tests/test_bookkeeping_addons.py::test_create_order_503`). This is a 503, distinct from the CF 52x error seen on the old live site.

## Root cause
Two independent issues:
- **A. Domain not cut over.** `ledgerkit.in` / `www.ledgerkit.in` are attached to this job's deployment but their Cloudflare custom-hostname SSL is still `initializing` / `verified:false`, so traffic still goes to the OLD deployment (the ₹199 build that emits the CF 52x checkout error). This job's latest ₹297 build is only reachable at `https://ledgerkit-live.emergent.host`.
- **B. Missing payment secrets.** This deployment's production secrets have no `RAZORPAY_KEY_ID` / `RAZORPAY_KEY_SECRET`, and the pulled preview `.env` never contained them. Once the domain cuts over, `POST /api/checkout/create-order` will return 503 until these keys are set — under the names THIS build reads (`RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET`), not `PAYMENT_LIVE_KEY_*`.

## What is needed for ledgerkit.in to serve this job's latest build
1. Complete custom-hostname verification/SSL for `ledgerkit.in` + `www.ledgerkit.in` on THIS deployment (`ledgerkit-live`). DNS already resolves (linked:true); SSL is still initializing. If it stays stuck because the OLD deployment still owns the Cloudflare custom hostname, that ownership must be detached from the old deployment — escalate to Emergent support (Platform) with both deployment/job IDs.
2. Add `RAZORPAY_KEY_ID` and `RAZORPAY_KEY_SECRET` (live values) in Deployment Panel → Secrets for `ledgerkit-live`, then redeploy, so checkout works after cutover.

## Verified vs inferred
- Verified: deployment exists & healthy; route present (405); no backend errors in logs; Razorpay secrets absent; source reads only RAZORPAY_KEY_ID/SECRET; combo price 297 in this build; domains unverified/SSL initializing.
- Inferred (not directly reproducible without the old job's scope / live keys): that the CF 52x error is produced by the old deployment; that the old deployment holds the active custom hostname. Could not reproduce the live Razorpay call (no keys / no live DB in sandbox).
